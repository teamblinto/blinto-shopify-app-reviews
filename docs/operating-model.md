# Shopify App Review — Operating Model

This document defines Blinto's approved lightweight operating model for the current Shopify App Review pilot. The Core Strategy + SOP 1–7 in `source-sops/` remain the detailed knowledge base; the execution layer intentionally minimizes routine handoffs so the team can publish, learn, and improve quickly.

## 1. Objective

Build useful, evidence-based Shopify app reviews consistently without creating an editorial process heavier than the content itself.

The pilot principle is:

**One owner → one review → one final SEO/quality check → publish.**

## 2. Source of Truth

1. `source-sops/` — detailed strategy, research, writing, publishing, and maintenance guidance.
2. `docs/` — approved practical execution model.
3. `templates/` — working review structure.
4. GitHub review records — evidence and content source of truth.
5. ClickUp — assignment, due date, stage, and blockers.
6. Review Hub — team-facing navigation and preview.

The source SOPs are not edited by this simplification. Where they describe more detailed review roles/gates, the pilot execution model consolidates those routine checks into the final SEO/quality check and uses specialist escalation only when genuinely required.

## 3. Ownership

Each review has **one primary author/assignee**. The author owns the complete creation cycle:

**Research & Testing → Evidence → Brief as needed → Writing → Self-check → Corrections**

The author's normal Blinto role does not limit what they evaluate.

### Final SEO/Quality Check

**Owner: Shemanto or, later, a calibrated SEO Agent.**

This is the only routine review handoff in the pilot. It checks SEO readiness plus obvious editorial, evidence, disclosure, and quality issues. It does not replace specialist judgment when a material technical/legal/reputational issue genuinely needs escalation.

### Publish

**Owner: Fazle or Shemanto.**

Once the final SEO/quality check passes, the article moves to Ready to Publish and can be published. There is no separate routine Technical Review, Revision, or Final Approval stage.

## 4. Approved Production Workflow

**Assigned → Research & Write → SEO Check → Ready to Publish → Published → Monitoring**

The author performs self-check before moving the task to SEO Check.

If Shemanto requests changes, the task stays in **SEO Check**. The original author resolves the feedback and resubmits. Do not create a separate Revision status.

## 5. Status Ownership

The person handing the work to the next owner changes the ClickUp status:

- Fazle/Shemanto assigns the review → **Assigned**
- Author begins → **Research & Write**
- Author finishes + self-checks → **SEO Check**
- Shemanto/SEO Agent passes the gate → **Ready to Publish**
- Fazle/Shemanto publishes → **Published**
- Publisher/maintenance owner activates ongoing tracking → **Monitoring**

Planning, category selection, SEO topic validation, distribution strategy, and program-improvement tasks belong in **Shopify GTM Execution**, not the review-production board.

## 6. Evidence & Testing Standard

Every review must state the actual evaluation level:

1. Full Hands-On Test
2. Partial Hands-On Test
3. Demo and Documentation Review
4. Research-Only Evaluation
5. Insufficient Evidence

Never present partial/documentation research as full hands-on testing. Keep developer claims, Blinto observations, and merchant feedback distinct. Verify and date pricing. Mark missing evidence rather than filling gaps by assumption.

## 7. AI Rule

**The author owns the review. AI assists the author; it does not become the author.**

AI may organize research, summarize verified evidence, help structure the article, draft from verified inputs, edit, and perform QA. AI must never fabricate research, testing, product behavior, screenshots, pricing, merchant feedback, quotations, statistics, scores, citations, or technical verification.

## 8. Editorial Independence

Founder relationships, partnerships, sponsorships, affiliate opportunities, discounts, free access, or potential Blinto business cannot control the review conclusion. Factual corrections can be considered and independently verified; external parties do not control pros/cons, rankings, verdicts, or publication decisions.

## 9. System Responsibilities

**GitHub** — content, evidence, SOPs, templates, assistant policy, and version history.

**ClickUp** — one task per review; owner, due date, current stage, blockers, and follow-up.

**Review Hub** — human-friendly strategy/process access, review status, and private preview.

**Future WordPress CMS** — publishing backend for public blog content.

**Public Blinto Astro website** — presentation layer consuming approved CMS content through API.

## 10. Validation Before Scale

Start with the five-author pilot and optimize for learning and publishing velocity. Do not build process complexity before observed quality or operational problems justify it.

The broader SOP 7 validation target remains 10 pieces: 3 category/bulk reviews, 5 single-app reviews, and 2 comparison articles. Scale toward 100 only after the program shows useful SEO/business outcomes and a repeatable production model.

## 11. Non-Negotiables

- One primary author/assignee per review.
- Author owns research, testing, evidence, writing, self-check, and corrections.
- One routine final SEO/quality gate: Shemanto or SEO Agent.
- Fazle or Shemanto publishes after that gate passes.
- Specialist review is escalation-based, not a routine board stage.
- No separate Revision or Final Approval status.
- No fabricated evidence or experience.
- Testing level and limitations must be transparent.
- Pricing/time-sensitive facts must be verified.
- SEO cannot override truthfulness or merchant usefulness.
- Publication is followed by monitoring and maintenance.
- Keep the pilot simple; add gates only when evidence shows they are needed.
